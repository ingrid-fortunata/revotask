# RevoTask HTTP API · Draft contract

Routes below are Flask endpoints relative to `API_BASE_URL`, which contains the origin only. Browser calls go through same-origin Next.js handlers with matching paths, except that the login response contains only the public user DTO. Server Components use the same Flask contract through the server-only client. See the [backend contract](../backend/specs/api-contract.md) for Blueprint ownership, validation schemas and stable error codes. Update examples from tested requests before submission.

## Request and response conventions

- JSON bodies use `Content-Type: application/json`. Reject unknown fields, invalid UUIDs and unsupported values with 400. A malformed JSON body returns 400, a missing or non-JSON `Content-Type` returns 415 and a body over 64 KiB returns 413. Query inputs are validated and pagination caps are applied.
- Flask public routes are health, register and login. All other Flask routes use `Authorization: Bearer <access-token>`. For browser writes, the Next handler verifies exact Origin.
- Success returns `{"data": ...}`. Delete and logout operations without response metadata return 200 with `{"data": null}`. Error example: `{"error":{"code":"VALIDATION_ERROR","message":"Check the submitted fields.","fields":{"title":"Required."},"request_id":"example-id"}}`. Omit `fields` where inapplicable. Timestamps are ISO 8601 UTC. PATCH modifies only submitted fields, except that explicit null clears fields documented as nullable.
- Status conventions: 400 invalid input, 401 invalid authentication, 403 forbidden, 404 missing/deleted resource, or a board the caller is not an active participant of (E07–E12 use the same 404 for nonmembers; E11 adds `USER_NOT_FOUND` for an unregistered email), 405 method not allowed (the response keeps the `Allow` header), 409 duplicate or state conflict, 413 request body too large (`CONTENT_TOO_LARGE`), 415 unsupported content type (`UNSUPPORTED_MEDIA_TYPE`), 429 rate limited, 503 unavailable. Unexpected internal errors return sanitized 500. Field limits below use trimmed length for names, titles and content. Preserve password bytes as entered.

## Endpoints

| ID | Method and path | Request → successful result |
|---|---|---|
| E01 | GET `/api/health` | Public → 200 status; bounded DB check, 503 on failure. |
| E02 | POST `/api/auth/register` | Public. Exactly `name` 1–80, valid `email` ≤254, `password` 8–128 with at least one uppercase letter, one lowercase letter and one ASCII special character (a space does not count); any other field is 400. `name` and `email` are trimmed, `email` is lowercased, `password` is kept as entered → 201 public user. Duplicate normalized email 409. |
| E03 | POST `/api/auth/login` | Public. Exactly `email` ≤254 and `password` 1–128 with no composition rule; any other field is 400 → 200 `{access_token,expires_in,user}` on Flask. On Next the body is `{"data":{"user"}}` and the handler sets the session cookie. Bad credentials 401. |
| E04 | POST `/api/auth/logout` | Authenticated → 200 after JWT revocation. The Next handler also returns 200 and clears the cookie when the cookie is absent or the session is already invalid. It returns 503 and keeps the cookie when revocation fails. |
| E05 | GET `/api/boards` | Accessible active board summaries, sorted by name and ID → 200. |
| E06 | POST `/api/boards` | `name` 1–100 → 201 board summary with admin membership. |
| E07 | GET `/api/boards/{id}` | Participant → 200 board with role, version, columns and nested cards. |
| E08 | PATCH `/api/boards/{id}` | Admin. `name` 1–100 → 200 updated board. |
| E09 | DELETE `/api/boards/{id}` | Admin → 200 with `{"data": null}`; the board is soft-deleted. |
| E10 | GET `/api/boards/{id}/members` | Participant → 200 active participants with public IDs, names and board roles. |
| E11 | POST `/api/boards/{id}/members` | Admin. Registered `email` → 201 membership; a previously removed user is reactivated as `member` with 201; already active 409 `STATE_CONFLICT`; unregistered email 404 `USER_NOT_FOUND` (plain envelope, no `fields`, returned only to an admin of the board). |
| E12 | DELETE `/api/boards/{id}/members/{user_id}` | Admin → 200 with `{"data": null}`; the membership is removed and the user's assignments on active cards in active columns of this board are cleared in the same transaction. Soft-deleted cards, cards in soft-deleted columns and other boards are unaffected. Target without an active membership 404; admin removal 409 `STATE_CONFLICT`. |
| E13 | POST `/api/boards/{id}/columns` | Admin. `name` 1–80, optional `is_done` default false → 201 `{column, position_version}`; the column is appended at the end. `is_done` true while the board has a Done column 409 `STATE_CONFLICT`. |
| E14 | PATCH `/api/columns/{id}` | Admin. `name`, `is_done`, at least one → 200 column; `position_version` does not change. Changing `is_done` on a nonempty column, or setting it true while another Done column exists, returns 409 `STATE_CONFLICT` and writes nothing. Submitting the current `is_done` value is not a change; other valid fields in the request still apply. |
| E15 | DELETE `/api/columns/{id}` | Admin → 200 with `{"data": {"position_version": n}}`. Nonempty column 409 `STATE_CONFLICT`. |
| E16 | PATCH `/api/boards/{id}/columns/reorder` | Admin. `column_id,before_column_id,expected_position_version` → 200 `{columns, position_version}` with every active column in authoritative order. An unchanged position returns 200 with the same version and writes nothing. A `column_id` that is not an active column of this board 404. |
| E17 | POST `/api/columns/{id}/cards` | Participant. `title` 1–160, optional nullable `description` ≤2,000 (blank is stored as null), optional nullable `assignee_id` → 201 `{card, position_version}`; the card is appended at the end. An `assignee_id` that is not an active participant of the board 400 `VALIDATION_ERROR` with `fields.assignee_id`. A new assignee other than the caller and the previous assignee is notified in the same transaction (C28). |
| E18 | PATCH `/api/cards/{id}` | Participant. Editable fields from E17, at least one → 200 card; column, order and `position_version` do not change. The `assignee_id` rule of E17 applies. A new assignee other than the caller and the previous assignee is notified in the same transaction (C28). |
| E19 | DELETE `/api/cards/{id}` | Participant → 200 with `{"data": {"position_version": n}}`; the card is soft-deleted. |
| E20 | PATCH `/api/cards/{id}/position` | Participant. `column_id,before_card_id,expected_position_version` → 200 `{card, columns, position_version}`. An unchanged position returns 200 with the same version and writes nothing. |
| E21 | GET `/api/cards?assignee=me` | Signed-in user → 200 unpaginated list of every active card assigned to the caller, on active boards where the caller has an active membership, each with `board_id` and `board_name`. Includes cards in the Done column. Excludes soft-deleted cards and cards in soft-deleted columns. Sorted by case-insensitive board name, board ID, column order, card order, then card ID. No match returns an empty list. `assignee=me` is the only accepted query (see the query rule below). Read-only. |
| E22 | GET `/api/boards/{id}/cards/search?q=...` | Participant. `q` 1–100 characters after trimming → 200 up to 20 active title matches (`id`, `title`, `column_id`), case-insensitive, with `%`, `_` and `\` matched literally, in board order (column order, card order, then card ID). No total. Title only: a description or comment word does not match. No match returns an empty list. A missing, deleted or inaccessible board returns the same 404 as E07 (nonmember, removed member). Read-only. |
| E23 | GET `/api/cards/{id}/comments` | Participant → 200 unpaginated list of active comments sorted by creation time and ID, each with the author's current name. An empty card returns an empty list. |
| E24 | POST `/api/cards/{id}/comments` | Participant. `content` 1–2,000 after trimming (inner line breaks kept) → 201 comment. Records one `comment_created` event in the same transaction. `created_at` and `updated_at` are equal on creation. The server does not deduplicate: two identical posts create two comments. A card assignee other than the author is notified in the same transaction (C28). |
| E25 | PATCH `/api/comments/{id}` | Author with current access. `content` 1–2,000 after trimming → 200 comment. `updated_at` changes only when the trimmed content changes; the same content returns 200 and writes nothing. A participant who is not the author, an admin included, gets 403 `FORBIDDEN`. |
| E26 | DELETE `/api/comments/{id}` | Author with current access → 200 with the comment as it was before the delete in `data`. Later reads omit it, and a repeat returns 404. A non-author participant, an admin included, gets 403 `FORBIDDEN`. |
| E27 | GET `/api/notifications?page=1&per_page=20` | Current user. `page` 1 to 2,147,483,647 (default 1) and `per_page` 1 to 50 (default 20), each sent once → 200 `{items,page,per_page,total,unread_count}`; newest first (`created_at` descending, then `id` descending). `total` and `unread_count` count all of the caller's visible notifications, whatever the page, and are present on an empty page. A page past the end returns an empty `items` list (C31). Read-only. |
| E28 | PATCH `/api/notifications/{id}/read` | Recipient with current access. No request body → 200 with the Notification item in `data`. The first call sets `read_at`. A repeat returns 200 with the original `read_at` and writes nothing. A missing, another user's or hidden notification returns 404 `NOT_FOUND` (C32). |
| E29 | GET `/api/boards/{id}/analytics` | Participant → 200 `{week_start,week_end,cards_per_column,completed_cards,member_activity}` for the current UTC week. `week_start` and `week_end` are ISO 8601 UTC timestamps ending in `Z`, from Monday 00:00 inclusive to the next Monday 00:00 exclusive. `completed_cards` counts distinct cards with an `entered_done` event that are still active cards in the Done column. `member_activity` counts `card_created`, `card_moved`, `column_reordered` and `comment_created` events by actor. Accepts no query parameter (400). Read-only (C34–C38). |
| E30 | GET `/api/users/me` | Current user → 200 `{id,name,email}`. |
| E31 | PATCH `/api/users/me` | Current user, own row only. A JSON object with `name`, `email` or both (E02 constraints, trimmed, email lowercased); an omitted field is not changed → 200 public user (`id`, `name`, `email`). `{}`, a non-object body, any other key (`password` included, `fields.<key>` = "Unknown field.") and an invalid value are 400. A duplicate email is 409 `EMAIL_ALREADY_EXISTS` from `uq_users_email` and nothing changes. Values equal to the stored ones after normalization return 200 and write nothing (`updated_at` unchanged). |

E21 and E22 query rule: each accepts only its documented parameter, sent once. A missing, repeated, invalid or unknown parameter returns 400 `VALIDATION_ERROR`. A known parameter carries `fields.assignee` or `fields.q` ("Required.", "Must be me.", "Must be at most 100 characters.", "Enter valid text." for a NUL character, "Send one value." for a repeat). An unknown parameter returns the standard message "Check the submitted fields." with no field entry for it. Check order: authenticate (401), path ID (400), query (400, before any database read), then board access for E22 (404). Both endpoints are read-only: no board lock, event, notification or `position_version` change. The same-origin browser handler for E22 forwards the query string unchanged, so Flask performs this validation.

E15 and E19 return position metadata for synchronizing clients. E16 and E20 require a nonnegative integer version (0 to 2147483647, not a boolean) and an explicit nullable anchor. Order conflicts return `POSITION_CONFLICT` with 409.

Check order for E13–E20: authenticate (401), validate path IDs and the body shape (400), resolve the board and check the caller's access (404 for a nonmember, 403 for a member on E13–E16), take the board lock, recheck membership, role and the addressed resource under the lock (404), compare the version (409 `POSITION_CONFLICT`), then validate the destination and anchor. An invalid destination column, an anchor that is the card itself, deleted, in another column or on another board returns 400 `VALIDATION_ERROR` with the fixed message "Choose a valid destination." and no `fields`, so nothing about another board is disclosed. The source resource is the card (E18–E20), the column (E14, E15) or, for E16, the `column_id` in the body; a missing source returns the normal 404.

Only a request that changes a position, or creates or deletes a column or card, changes `position_version` (by 1). E14, E18 and an unchanged E16 or E20 leave it alone. When `position_version` is already 2147483647, a request that would change it returns 409 `STATE_CONFLICT` with a fixed message and writes nothing; reads still work. Events (`card_created`, `card_moved`, `column_reordered`, `entered_done`) are written in the same transaction and only for a real change. `entered_done` is written for a card created in a Done column and for a card moved from a column that is not Done into the Done column.

Comment check order for E23–E26: authenticate (401), validate path IDs and the body shape (400), resolve the board from the card or comment through the parent chain and check the caller's access (404 for a nonmember or a removed member, including a removed author). E24–E26 then take the board lock, recheck membership, reload the card or comment under the lock (404 when missing, soft-deleted or on an inactive card), and only then check authorship for E25 and E26 (403). Comment writes do not change `position_version`. Only E24 records an event (`comment_created`); edit and delete record none and do not remove the earlier event. Content is plain text: the server stores the trimmed text and never interprets HTML or Markdown. A blank, non-text, over-long or unknown field returns 400 with `fields.content` where a field applies.

E31 clarifications (C23–C27): it is a partial update of `name`, `email` or both, and `{}` is 400 with the standard message and no field entry (C23). A submitted value that equals the stored one after normalization is a no-op: 200, no write, `updated_at` unchanged, and a case-only change of the caller's own email is a no-op and not a 409 (C24). The update is all or nothing: a duplicate email is 409 and a valid `name` sent beside it is not stored (C25). Last write wins per submitted field, a field that is not submitted is never written, and both submitted fields are applied together while the user row is locked (C26). A key other than `name` and `email` is rejected with `Unknown field.`, an email change revokes no token and sends no mail, and the 409 gives a signed-in user an additional account-enumeration path next to E02 (C27). Reauthentication for an email change, confirmation of the new address, a notice to the old address and an E31 rate limit are deferred to T16 for public release.

Notification clarifications (C28–C33): a new assignment (E17, E18) notifies the new assignee when they differ from the caller and from the card's previous assignee, and a new comment (E24) notifies the card's current assignee when they differ from the author. Nothing else notifies: not the caller's own action, an unchanged or cleared assignee, an unassignment, a move, an edit or delete of a card or comment, or the removal of a member. The row is written in the same transaction as its change, under the board lock, so a rolled-back change leaves none (C28). Each qualifying event creates one notification, with no collapsing or deduplication, so `unassigned → A → B → A` by another user notifies A twice (C29). One visibility filter applies to E27 items, `total`, `unread_count` and E28: an active board, column and card, and the recipient's active membership. Rows are kept, so a member who is removed and added again sees them again with their original `read_at` (C30). E27 accepts only `page` and `per_page`, each sent once as digits (no sign, no leading zero, no decimal). A missing parameter takes its default. A repeated, unknown or invalid parameter returns 400 `VALIDATION_ERROR`, with `fields.page` or `fields.per_page` for a known parameter and the standard message for an unknown one, before any database read. The offset is computed in 64-bit arithmetic, so the largest accepted values return an empty page with 200 (C31). E28 reads no body and takes no board lock. It updates only a row that the caller owns, that is unread and that passes the visibility filter, and it returns the item. Two concurrent calls keep one `read_at` (C32). The item adds `actor_name`, `board_name` and `card_title`, current values resolved on read for visible rows only. Every earlier field stays (C33). Check order for E27: authenticate (401), query (400), read. For E28: authenticate (401), path ID (400), update and lookup (404). There is no endpoint to mark all read, delete or mark unread in v1. The bell polls E27 every 30 seconds while mounted.

Analytics clarifications (C34–C38): the Week is the UTC calendar week of the server clock when the request is handled, Monday 00:00:00 UTC inclusive to the next Monday 00:00:00 UTC exclusive. An event at `week_start` is inside the Week and one at `week_end` is outside. `week_start` and `week_end` are ISO 8601 UTC timestamps that end in `Z`, for example `2026-11-09T00:00:00Z` (C34). `completed_cards` is the number of distinct card IDs with an `entered_done` event on the board in the Week that are still active cards in an active Done column when the request is handled. A card counts once however often it entered Done, and it stops counting when it is deleted, moved out of Done or its column stops being Done (C35, revised 2026-11-17). `member_activity` counts four event kinds, `card_created`, `card_moved`, `column_reordered` and `comment_created`. `entered_done` is used for `completed_cards` only, so creating a card in Done or moving a card into Done adds one activity event. It lists every actor with a counted event in the Week, a former board member included, under the actor's current name, sorted by `count` descending, lower-cased `name`, then `user_id`. An actor with no counted event is omitted, and the list is empty when the Week has none (C36). `cards_per_column` lists every active column in board order (column order, then column ID) with its active card count, 0 for an empty column, and is an empty list when the board has no active column. A deleted card or column is not counted or listed (C37). E29 takes no query parameter and no body. Any query parameter returns 400 `VALIDATION_ERROR` with the standard message and no field entry, before any read. Check order: authenticate (401), board ID (400), query (400), board access (404, the generic envelope of C1). It is read-only: no board lock, event, notification or `position_version` change, and the response is `private, no-store`. Every current participant, member or admin, may read it (C38).

## Representative data shapes

```text
BoardSummary { id, name, role, position_version }
BoardDetail { ...BoardSummary, columns: ColumnWithCards[] }
Column { id, board_id, name, is_done, order }
ColumnWithCards { ...Column, cards: Card[] }
Card { id, column_id, title, description, assignee_id, assignee_name, order }
Comment { id, card_id, author_id, author_name, content, created_at, updated_at }
Notification { id, kind, board_id, card_id, actor_id, actor_name, board_name, card_title, created_at, read_at }
E13 { column: Column, position_version }
E17 { card: Card, position_version }
E16 { columns: Column[], position_version }
E20 { card: Card, columns: ColumnWithCards[], position_version }
E29 data { week_start, week_end, cards_per_column: [{ column_id, name, count }], completed_cards, member_activity: [{ user_id, name, count }] }
E29 cards_per_column item { column_id, name, count }
E29 member_activity item { user_id, name, count }
E21 item { ...Card, board_id, board_name }
E22 item { id, title, column_id }
E10–E11 membership { user_id, name, role }
```

For E20, send only affected active column lists. For `assignee_name` and other nullable card fields, return null when cleared. Use explicit serialization allowlists for every public response.
